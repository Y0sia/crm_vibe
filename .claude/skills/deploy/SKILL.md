# Деплой CRM на VPS

Продакшен — один VPS (Ubuntu 22.04, 1 CPU, 1 ГБ RAM + 2 ГБ swap). Собирать образы там нельзя —
не хватит памяти, поэтому `scripts/deploy.sh` собирает их на этой машине под `linux/amd64`
и отправляет на сервер.

## Что на сервере

- SSH: `ssh crm-vps` (алиас в `~/.ssh/config`, ключ `~/.ssh/crm_vps_ed25519`; вход по паролю отключён).
- Приложение: `/opt/crm` — `docker-compose.yml` (копия `docker-compose.prod.yml`), `.env` с паролями
  и `CRM_TAG` — версией образов (только на сервере, не читать в чат и не коммитить), `DEPLOYED` — текущий коммит, `deploy.log` — история.
- Контейнеры (проект `vibe-crm-prod`): `postgres` (том `vibe-crm-prod_postgres-data`), `backend`, `frontend`
  (слушает только `127.0.0.1:8080`). Снаружи — nginx хоста на 80 (`deploy/nginx/crm.conf` → `/etc/nginx/sites-available/crm`).
- Резервные копии базы: каждую ночь в 03:30 → `/opt/crm/backups` (14 дней), скрипт `deploy/backup.sh`.
- Открыты только 22, 80, 443 (ufw); fail2ban на SSH.

## Главное правило: postgres не трогать

Пользователь явно запретил трогать базу при деплое. Поэтому никогда:
- `docker compose down` (тем более `down -v`), `docker volume rm`, `docker system prune --volumes`;
- `docker compose up` без явного списка `backend frontend` и без `--no-deps`;
- рестарт, пересоздание или обновление образа `postgres`.

Если для изменения нужно трогать базу (новая версия Postgres, смена её настроек) — остановись
и спроси пользователя, предложив сначала сделать резервную копию (`ssh crm-vps /opt/crm/backup.sh`).
Миграции Liquibase трогать базу можно — они применяются бекенд­ом при старте.

## Процесс

1. **Что выкладываем.** «Актуальная версия» — ветка `main` на GitHub. Проверь:
   - `git status` — если есть незакоммиченные изменения, которые пользователь хочет выложить,
     сначала закоммить и запушь их по скиллу `github-push`;
   - `git fetch && git log --oneline origin/main..origin/dev` — если в `dev` есть коммиты, которых нет
     в `main`, спроси: влить `dev` в `main` (fast-forward) и выложить, или выложить `main` как есть.
     Выложить `dev` напрямую можно только по явной просьбе: `scripts/deploy.sh dev`.
2. **Убедись, что Docker запущен локально** (`docker info`). Локальный бекенд на время работы
   прода запускать нельзя: один токен бота — один получатель сообщений.
3. **Выкладка:** `scripts/deploy.sh` (запускай в фоне — тесты, сборка и отправка занимают 3–6 минут).
   Скрипт сам: берёт `origin/main`, прогоняет тесты бекенда и фронтенда, собирает образы,
   отправляет их, перезапускает только `backend` и `frontend`, ждёт `healthy` и проверяет сайт.
   Если тесты не прошли — выкладка отменяется, доложи причину.
4. **Проверка после выкладки:**
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' http://91.228.153.163/            # 200
   curl -s -o /dev/null -w '%{http_code}\n' http://91.228.153.163/api/auth/me  # 401
   ssh crm-vps 'cd /opt/crm && docker compose ps && cat DEPLOYED'
   ```
5. **Отчёт пользователю** простыми словами: какая версия выложена (коммит и его описание), что
   проверено, сайт открывается.

## Если что-то пошло не так

- Бекенд не стал `healthy` — скрипт печатает хвост журнала. Подробнее:
  `ssh crm-vps 'cd /opt/crm && docker compose logs --tail 100 backend'`.
- Откат на прошлую версию (на сервере хранятся текущая и предыдущая):
  `ssh crm-vps cat /opt/crm/deploy.log`, затем `scripts/deploy-rollback.sh <коммит>`.
- Изменился `.env.production.example` (новые переменные) — добавь их в `/opt/crm/.env` на сервере
  до выкладки, не выводя содержимое файла в чат.
- Изменились `deploy/nginx/crm.conf` или `deploy/backup.sh` — скопируй их на сервер вручную
  (`scp`, затем `nginx -t && systemctl reload nginx`), скрипт деплоя их не обновляет.

# CRM для лидов из Telegram — дизайн v1

Дата: 2026-10-14. Источник UI: `design.html` в корне репозитория (12 экранов: 5 десктопных, 7 мобильных; бандл, тексты/данные экранов лежат во вложенных gzip-шаблонах).

## Цель

Каждый, кто пишет в личные сообщения рабочему Telegram-аккаунту компании, автоматически становится лидом в CRM. Менеджеры ведут лидов по воронке статусов, размечают тегами, отвечают из CRM; руководитель видит статистику на дашборде.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Интеграция с Telegram | Telegram Business «чат-бот» (секретарь): бот `@crm1423bot` подключается к Premium-аккаунту компании. Не MTProto/api_id. |
| Аккаунтов | Один общий аккаунт компании |
| Кто лид | Любой, кто написал в личку. Исключений нет |
| История | Только новые сообщения, импорта старых переписок нет |
| Источник | Ручное поле, фиксированный список: `CHANNEL` «Канал», `GROUP` «Группа», `ADS` «Реклама», `REFERRAL` «Сарафан», `OTHER` «Другое»; по умолчанию не указан |
| Роли | `ADMIN` — всё, включая настройки и пользователей; `MANAGER` — работа с лидами (все лиды видны), без экранов настроек |
| Назначение менеджера | Вручную; новый лид «Не назначен» |
| Медиа | Только текст. Подпись к медиа сохраняется, вместо файла — пометка «[Фото]», «[Голосовое сообщение]» и т.п. Исходящие из CRM — только текст |
| Время ответа | Считается каждый ответ (см. «Время ответа») |
| Учётные записи | Создаёт администратор; вход по логину и паролю |

## Ограничения Telegram Business (проверено по Bot API 10.3)

- Бот получает только личные чаты бизнес-аккаунта (`business_message`, `edited_business_message`, `deleted_business_messages`), группы и каналы — нет.
- Ответ от имени аккаунта (`sendMessage` с `business_connection_id`) возможен, только если у подключения есть право `can_reply`, и только в чаты, где было входящее сообщение за последние 24 часа.
- Телефон лида доступен только если лид прислал контакт (`message.contact` с `user_id` = лид).
- Требуется Telegram Premium на аккаунте и включённый Business Mode у бота (`getMe.can_connect_to_business = true` — уже так).
- Предположение, которое проверяется при первом живом подключении: сообщения, которые владелец аккаунта пишет из приложения Telegram, тоже приходят боту как `business_message` (`from.id` = владелец). Если нет — такие ответы не попадут в CRM; на остальное это не влияет.

## Архитектура

Существующий каркас: Spring Boot 4.1 / Java 25 (`backend/`), React 19 + Vite (`frontend/`), PostgreSQL 18 в docker compose, Liquibase. Фронт ходит на `/api` через прокси Vite.

### Бекенд — пакеты (`com.vibe.crm.*`)

Каждый пакет — отдельная область со своими сущностями, сервисом и контроллером.

- **`auth`** — Spring Security, сессия в cookie, хранится в Postgres (Spring Session JDBC). JSON-эндпоинты `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`. CSRF включён в режиме SPA (cookie `XSRF-TOKEN` → заголовок `X-XSRF-TOKEN`). Неавторизованный запрос → 401 (без редиректа). Пароли — BCrypt.
- **`users`** — `users`: `id`, `login` (уникальный, без учёта регистра), `password_hash`, `display_name`, `role`, `active`, `created_at`. Админ-API `/api/admin/users`: список, создание, изменение имени/роли, смена пароля, блокировка/разблокировка. Нельзя заблокировать или понизить самого себя и последнего активного администратора. Заблокированный пользователь не может войти, его активные сессии удаляются. **Первый администратор**: при старте, если таблица пуста, создаётся пользователь из `CRM_ADMIN_LOGIN` / `CRM_ADMIN_PASSWORD` (`.env`); если переменных нет — приложение не стартует с понятной ошибкой.
- **`statuses`** — `statuses`: `id`, `name` (уникальный), `color` (ключ палитры), `position`, `won` (boolean). Сид: Новый (blue), В работе (orange), Ждёт ответа (purple), Квалифицирован (teal), Сделка (green, `won=true`), Отказ (gray). Палитра из дизайна: blue, orange, purple, teal, green, pink, yellow, gray (точные `dot/bg/fg` — в `design.html`, экран «Настройки — статусы»). CRUD + переупорядочивание (`PUT /api/statuses/order` со списком id). Удаление: лиды переходят в первый по порядку оставшийся статус (с записью в историю); последний статус удалить нельзя. Если удалён статус с `won=true`, «Сделки» на дашборде показывают «—». Чтение — всем, изменение — `ADMIN`.
- **`tags`** — `tags`: `id`, `name` (уникальный), `color`. Сид: VIP, Опт, Розница, Повторный, Срочно с цветами из дизайна. CRUD; удаление снимает тег со всех лидов. Чтение — всем, изменение — `ADMIN`.
- **`telegram`** — тонкий клиент Bot API на `RestClient`: `getUpdates`, `sendMessage`, `getBusinessConnection`. `UpdatePoller` — фоновый long polling (`timeout=25`, `allowed_updates=[business_connection, business_message, edited_business_message, deleted_business_messages]`), offset хранится в БД (`telegram_state`), чтобы не терять и не повторять апдейты после перезапуска. Каждый апдейт обрабатывается в своей транзакции; ошибка одного апдейта логируется и не останавливает цикл. Без `TELEGRAM_BOT_TOKEN` поллер не запускается (предупреждение в логе), остальное приложение работает. `business_connections`: `id` (строковый id подключения), `owner_telegram_user_id`, `can_reply`, `enabled`, `updated_at`.
- **`leads`** — `leads`: `id`, `telegram_user_id` (уникальный), `telegram_chat_id`, `business_connection_id`, `first_name`, `last_name`, `username`, `phone`, `status_id`, `manager_id` (null = не назначен), `source` (null = не указан), `created_at`, `last_message_at`, `last_message_text`, `last_incoming_at`, `awaiting_reply_since`. `lead_tags` (многие-ко-многим). Имя/username обновляются из каждого входящего сообщения.
- **`messages`** — `messages`: `id`, `lead_id`, `telegram_message_id`, `direction` (`IN`/`OUT`), `text`, `sent_at`, `author_id` (менеджер, если отправлено из CRM), `edited_at`, `deleted`. Уникальность `(lead_id, telegram_message_id)` — повторный апдейт по уже сохранённому сообщению (в т.ч. эхо ответа, отправленного из CRM) игнорируется.
- **`history`** — `lead_events`: `id`, `lead_id`, `actor_id` (null = система), `type` (`CREATED`, `STATUS_CHANGED`, `MANAGER_CHANGED`, `SOURCE_CHANGED`, `TAG_ADDED`, `TAG_REMOVED`), `old_value`, `new_value` (текстом — имена на момент события, чтобы история читалась после переименования/удаления), `created_at`.
- **`responses`** — `response_events`: `id`, `lead_id`, `author_id` (null = ответ из приложения Telegram), `waited_seconds`, `answered_at`.
- **`dashboard`** — `GET /api/dashboard?from=&to=` (даты в часовом поясе `crm.timezone`, по умолчанию `Europe/Moscow`).
- **`events`** — SSE `GET /api/events`: события `lead.created`, `lead.updated`, `message.created` с id лида. Рассылаются после коммита транзакции. Фронт по событию перезапрашивает нужные данные.

### Обработка входящих апдейтов

1. `business_connection` → upsert в `business_connections`.
2. `business_message` в чате `type=private`:
   - отправитель ≠ владелец подключения → **входящее**: найти/создать лида по `from.id` (при создании: первый статус, без менеджера, событие `CREATED`, SSE `lead.created`), обновить имя/username, сохранить сообщение `IN`, обновить `last_message_*`, `last_incoming_at`; если `awaiting_reply_since` пуст — поставить время сообщения. Если сообщение — контакт самого лида, записать телефон.
   - отправитель = владелец → **исходящее из приложения**: лид по `chat.id`; если лида нет — игнорировать (лидом становится только тот, кто написал сам). Сохранить `OUT` без автора, учесть ответ (см. ниже).
3. `edited_business_message` → обновить текст и `edited_at` (если сообщение есть).
4. `deleted_business_messages` → пометить `deleted=true`; в переписке показываются как «Сообщение удалено».
5. Текст: `text` или `caption`; при медиа без подписи — пометка по типу (`photo` «[Фото]», `video` «[Видео]», `voice` «[Голосовое сообщение]», `video_note` «[Видеосообщение]», `audio` «[Аудио]», `document` «[Файл]», `sticker` «[Стикер]», `animation` «[GIF]», `contact` «[Контакт]», `location` «[Геопозиция]», прочее «[Вложение]»). Подпись и пометка объединяются: «[Фото] текст подписи».

### Ответ из CRM

`POST /api/leads/{id}/messages {text}` (1–4096 символов). Проверки: есть подключение с `enabled && can_reply`, `last_incoming_at` не старше 24 часов — иначе 409 с понятной причиной. `sendMessage` → сообщение `OUT` с `author_id` = текущий пользователь, учёт ответа, SSE. Ошибка Telegram → 502 с текстом причины, сообщение не сохраняется.

### Время ответа

При каждом исходящем сообщении (из CRM или приложения), если у лида `awaiting_reply_since` не пуст: записать `response_events(waited_seconds = sent_at − awaiting_reply_since, author_id)` и очистить `awaiting_reply_since`. Таким образом, серия сообщений лида — одно ожидание, первый ответ на неё — одно время ответа. Время ответа менеджера на дашборде — среднее по его `response_events` за период (по `answered_at`). Ответы без автора в статистику менеджеров не входят.

### API лидов

- `GET /api/leads` — фильтры: `q` (имя/username), `messageText` (текст последнего сообщения), `from`/`to` (дата последнего сообщения), `managerId` или `manager=none`, `source` (или `none`), `statusIds[]`, `tagIds[]` (любой из). Сортировка по `last_message_at` убыв. Пагинация по 25. Ответ: элементы, `total` (всего лидов без фильтров), `found` (с фильтрами), счётчики лидов по статусам (для чипов фильтра).
- `GET /api/leads/{id}` — карточка: данные, теги, менеджер, источник, признак «можно ответить из CRM» и причина, если нельзя.
- `GET /api/leads/{id}/messages` — переписка (по возрастанию времени, все).
- `GET /api/leads/{id}/events` — история (по убыванию).
- `PATCH /api/leads/{id}` — `statusId`, `managerId` (null = снять), `source` (null = снять); каждое изменение → событие истории + SSE.
- `POST /api/leads/{id}/tags/{tagId}`, `DELETE /api/leads/{id}/tags/{tagId}` → событие + SSE.
- `GET /api/leads/new-count` — число лидов в первом статусе (бейдж у пункта меню «Лиды»).
- `GET /api/users/managers` — активные пользователи для выпадающих списков (доступно всем).

### Дашборд

За период `[from, to]` (включительно, по дате в `crm.timezone`):
- **Новые лиды по дням** — по `created_at`, с нулями в пустые дни.
- **Лиды по статусам / источникам / тегам** — среди лидов, созданных в периоде, по их текущему состоянию. Источники — с долей в %, плюс «Не указан».
- **Менеджеры** — по каждому активному пользователю и строка «Не назначен»: лидов (созданных в периоде и назначенных на него), сделок (из них в статусе `won`), среднее время ответа (`—`, если ответов нет). Формат времени: «45 сек», «11 мин», «2 ч 5 мин».

Периоды в UI: 7 дней, 30 дней, квартал (90 дней), свой (с–по). По умолчанию 30 дней.

### Фронтенд

React Router, TanStack Query (кэш + перезапрос по SSE-событиям), вёрстка по `design.html`: шрифт Manrope, цвета и размеры из макетов, без UI-библиотеки и без библиотеки графиков (столбики и полосы — блоками, как в макете). Экраны: вход; дашборд; лиды (таблица + панель фильтров; на мобильном — карточки, фильтр отдельным экраном, «Показать ещё» вместо страниц); карточка лида (воронка, теги, данные, история, переписка, поле ответа или пояснение, почему ответ недоступен, кнопка «Открыть в Telegram» — `https://t.me/<username>`, если username есть, иначе `tg://user?id=<id>`); настройки статусов; настройки тегов; **пользователи** (нового экрана нет в дизайне — в стиле экрана тегов: список, форма создания, смена пароля, блокировка). Пункты «Настройки» и экран пользователей видны только `ADMIN`. Адаптивность: брейкпоинт 768px, мобильные экраны по макетам «Моб. — …».

## Ошибки и устойчивость

- Telegram недоступен / сеть — поллер повторяет с паузой (экспоненциально до 60 с), без потери offset.
- Ответ Telegram 401/404 на токен — ошибка в лог, поллер останавливается до перезапуска.
- Конфликт `getUpdates` (409 — вебхук или второй экземпляр) — в лог, повтор с паузой.
- Ошибки валидации API → 400 с полем и сообщением на русском; 403 для недостаточной роли; 404 для отсутствующих сущностей.

## Тестирование

- Бекенд: интеграционные тесты `@SpringBootTest` на **Testcontainers** PostgreSQL (отдельная БД на прогон, рабочая БД не трогается). Обработка апдейтов — на JSON-фикстурах реальной формы Bot API; клиент Telegram в тестах подменяется (`MockRestServiceServer` для самого клиента, фейк для остальных тестов). Покрываются: создание лида и дедупликация, исходящие/эхо, редактирование/удаление, пометки медиа, время ответа, правило 24 часов, фильтры списка, права ролей, удаление статуса/тега, расчёты дашборда, вход/выход/блокировка.
- Фронтенд: Vitest + Testing Library для форматирования и логики фильтров; `npm run build` и `npm run lint` чистые.
- Ручная проверка end-to-end с реальным ботом после подключения его к аккаунту.
